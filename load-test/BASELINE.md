## 다시 재는 방법

```bash
docker compose up -d                                   # MySQL·Redis·Prometheus·Grafana
JWT_SECRET=$(openssl rand -base64 48) JWT_ACCESS_TOKEN_SECONDS=7200 ./gradlew bootRun   # 30분 측정 중 토큰이 만료되지 않게 2시간
cd load-test
docker exec -i <mysql 컨테이너> mysql -uaccount -paccount --default-character-set=utf8mb4 accountSystem < seed.sql
docker run --rm -v "$PWD:/scripts" grafana/k6:0.54.0 run --summary-export /scripts/results/<날짜>-normal-summary.json /scripts/normal.js
docker exec -i <mysql 컨테이너> mysql -uaccount -paccount --default-character-set=utf8mb4 -t accountSystem < check.sql
# 같은 계좌 집중은 seed.sql을 다시 넣고 hot-account.js로 같은 순서
# 11-19 측정: 연결을 미리 맺고(-e WARM=1) 원자료를 남긴 뒤 percentiles.py로 백분위 계산. 다른 계좌 영향은 other-account.js
docker run --rm -v "$PWD:/scripts" grafana/k6:0.54.0 run -e WARM=1 --out csv=/scripts/results/<이름>.csv.gz /scripts/hot-account.js
python percentiles.py results/<이름>.csv.gz
```

- 측정 구간 그래프는 Grafana `StockAccount 기본` 대시보드에서 위 시각(평시 10:23:53~10:53:58, 집중 10:54:26~10:55:49, 한국 시각)으로 봄

### 측정 환경과 기준선과 다른 점

- 같은 계좌 집중·다른 계좌 영향은 `WARM=1`로 돌렸음. 첫 A 측정에서 300개 VU가 한 순간에 새 연결을 맺자 Docker Desktop의 호스트 연결이 회차마다 수십~백여 건을 `connection refused`로 거절했고, k6는 이 요청을 응답 시간 0으로 요약에 넣어 p50이 낮게 나왔음. 그래서 VU마다 연결을 먼저 맺은 뒤 한꺼번에 보내게 하고, 그 전의 측정은 버렸음. 기준선(11-18)은 이 선택 없이 쟀지만 그때 출금·매수 300건은 모두 응답을 받았음(성공+거절 = 300)
- p50·p95는 k6 요약이 아니라 원자료(`results/2026-11-19-*-hot-*.csv.gz`, `*-other-*.csv.gz`)에서 응답을 받은 요청만으로 다시 계산했고, 3회의 응답을 합쳐 계산함. 계산은 `percentiles.py`. 연결을 맺지 못한 요청은 아래 표에 따로 적음
- 평시는 30분이 아니라 5분(`DURATION=5m`)만 잼. 그래서 평시 숫자는 기준선과 나란히 놓지 않고 A·B·C끼리만 비교함. 평시 숫자는 k6 요약(`*-normal-summary.json`)이고 연결을 맺지 못한 요청은 단계마다 0~1건이었음
- 매 측정 직후 `check.sql`의 불일치는 A·B·C·C50 모든 회차에서 0건이었음

### 숫자가 이렇게 나온 이유 [추정]

- 같은 계좌 집중이 20초대에서 3~4초대로 줄었음. 변경 전에는 요청마다 계좌 행을 잠근 채 비밀번호 해시 비교를 해서 300건이 그 비교를 한 줄로 기다렸고, 변경 뒤에는 비교가 동시에 돌고 잠금 안에는 잔액 변경만 남았기 때문으로 봄
- 남은 3~4초는 같은 계좌 잔액 변경이 여전히 한 줄로 서기 때문으로 봄. 본 작업 트랜잭션은 계좌 잠금을 기다리는 동안 DB 연결을 쥐고 있어, 몰린 요청 10건이 연결 10개를 모두 잡고 나머지는 연결을 기다림. 연결 대기 최대 190개는 Tomcat 작업 스레드 200개에서 연결을 쥔 10개를 뺀 수와 같음
- 다른 계좌 요청도 몰아넣는 몇 초 동안은 같은 연결 줄에 서므로 p95가 대조군(수십 ms)보다 1~3초 길게 남음. 다만 p50은 대조군과 같아졌는데, 몰아넣는 시간이 20초대에서 몇 초로 줄어 그 시간에 걸린 요청이 적어졌기 때문으로 봄
- 연결을 50개로 늘려도 나아지지 않았음. 몰린 요청 수(300)가 연결 수보다 많으면 늘린 연결도 잠금을 기다리는 요청이 모두 쥐기 때문으로 봄. 그래서 풀 값은 기본값으로 두었고, 이 대기를 줄이려면 한 계좌에 동시에 들어오는 요청 수를 앞단에서 제한하는 쪽을 봐야 함
- B와 C는 같은 값이라 차이(출금 p50 2.9초 대 3.8초)는 회차 사이 흔들림으로 봄. C 안에서도 회차별 p50이 3.1~5.3초로 벌어졌음
- 평시의 비밀번호 요청(매수·매도·출금)은 단계마다 같았음. 비교를 잠금 밖으로 옮겼을 뿐 요청마다 해시 비교를 하는 시간은 그대로이기 때문임. 기준선보다 15~30ms 느린 것은 측정 길이·컨테이너가 달라서일 수 있으나 따로 확인하지 않았음
